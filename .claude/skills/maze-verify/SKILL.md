# Проверка перед заливкой (MAZE2027)

Проверка — только на настоящем роботе. **Симулятор (`sim/`) не используется:** он пропускал навигацию, которая плохо ехала на поле. Не запускать и не предлагать его. Локально — только быстрые проверки, потом заливка и заезд у пользователя.

Итог формулировать честно: «тесты и сборка прошли, на поле не проверено», пока пользователь не прислал результат заезда.

## 1. Локально — по тому, что менялось

| Менялось | Проверка |
|---|---|
| любой `.py` в `pi/` или корне | юнит-тесты + pyright по изменённым файлам |
| `src/`, `include/` | сборка ESP (`pio run`, хук делает сам; прошивка — скилл `esp-flash`) |
| протокол ESP↔Pi | обе стороны изменены и собраны: `robot_link.h/.c` и `pi/protocol.py`, `pi/esp_link.py` |

```bash
python3 -m unittest discover -s pi/tests 2>&1 | tail -3
pyright pi/<изменённые файлы>.py 2>&1 | tail -15
```

- `pi/tests` ≈1 с, пропуски «нужен numpy» — норма. Хук сам гоняет их после правки `pi/`.
- pyright: в репозитории есть старые ошибки. Сравнивать только изменённые файлы с их версией до правки; новых ошибок быть не должно, старые попутно не чинить.

## 2. Заливка

Через скилл `pi_connect` (сравнить с Pi, `.bak`, залить). Python на Pi — 3.11: без синтаксиса и API 3.12+.

## 3. Что дать пользователю для заезда

- Команду запуска (из `pi_connect`).
- 2–4 пункта «на что смотреть на поле» именно для этой правки: что должно измениться и в какой строке лога или на дашборде это видно (например, «на горке в логе `[RAMP]` один раз, а не четыре»).
- Что прислать обратно: вывод заезда (`nav.py`), при проблемах — лог с Pi; разбирать его скиллом `run-log-triage`.

## Правила проекта, которые проверка должна ловить

- Заезд кончается только на старте: в `nav.py` нет `FATAL`/`sys.exit` (хук `guard_rules.py` ловит сам).
- Для заезда в `src/main.c`: `BUTTON_TEST 0`, `DRIVE_TEST 0`, `RUN_MAZE 1` (тот же хук).
- Комплекты выдаются сразу у жертвы, не «потом».
- YOLO только камерой со стороны стены.
