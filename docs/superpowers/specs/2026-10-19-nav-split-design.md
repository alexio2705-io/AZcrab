# Разбор nav.py на небольшие модули

Дата: 2026-10-19. Ветка: `nav-split` (от `nav-oct7`, исходная точка — коммит `32ca25c`, это код, который сейчас стоит на Pi).

## Зачем

Пользователь хочет сам править логику движения робота: реакцию на бампер, доворот на метку, считывание лидара, отъезды. Сейчас это невозможно: `pi/nav.py` — 5439 строк и 155 функций в одном файле, `_drive_cells` — одна функция на 945 строк с ~80 локальными переменными. Логика бампера размазана по трём местам (константы в шапке, ловля нажатия внутри `_drive_cells`, реакция на удар дважды — в `flood_fill_run` и в `return_to_start`).

Цель — чтобы на соревновании он мог быстро открыть нужный файл, понять логику сверху вниз и переписать её сам.

## Цели

- Каждая тема движения — в своём небольшом файле в `pi/`, с одной задачей.
- Логика читается как список шагов. Простые функции, простые `if`/`while`, без хитрых конструкций (вложенные генераторы, лямбды в логике, декораторы, метапрограммирование, наследование).
- Числа, которые хочется крутить, стоят вверху того файла, где используются, с комментарием по-русски.
- Поведение робота **не меняется**.

## Не цели

- Дашборд, OLED, лифт-детектор, живая карта: переносятся из nav.py в отдельный файл как есть, внутри не трогаются.
- `pi/oled.py` и другие файлы вне nav.py не трогаются (кроме `pi/walls.py` на этапе 2, см. ниже).
- Симулятор (`sim/`) не запускается и не чинится. После разбора он перестанет работать, потому что подменяет функции внутри `nav` (`nav.time`, `nav.wait_telem`, `nav._link` и т. п.). Починить его — отдельная задача, если пользователь попросит.
- `pi/challenge.py` (технические испытания) не трогается, хотя он импортирует внутренности `nav` и сломается. Пользователь сказал, что испытания неактуальны.
- Прошивка ESP (`src/`) не трогается.

## Анти-цели (провал, даже если «работает»)

- Робот на поле ведёт себя иначе, чем до разбора.
- Новые файлы такие же большие и запутанные, только их стало больше.
- Появились «умные» абстракции: классы-иерархии, реестры, обёртки, которые новичок не прочитает.
- Что-то починено отключением фичи.

## Ограничения

- Python 3.11 на Pi (без API 3.12+). Новых зависимостей в venv на Pi не ставить.
- Симулятор не запускать.
- Правила проекта из `CLAUDE.md` действуют: заезд кончается только на старте, без FATAL, аптечки сразу у жертвы, YOLO только в сторону стены.
- Перед заливкой на Pi сравнить файлы на Pi с локальными и сделать `.bak`.

## Что решено

### Файлы (все в `pi/`)

| Файл | Что внутри |
|---|---|
| `nav.py` | Запуск и главный цикл (`main`), больше ничего |
| `state.py` | Общие изменяемые переменные робота: карта, посещённые клетки, курс старта, текущая клетка и т. п. |
| `config.py` | Только те константы, которые нужны сразу нескольким модулям (размер клетки и т. п.) |
| `esp_link.py` | Связь с ESP, поток телеметрии, команды моторам (`motors`, `stop`, `brake`, `zero_odo`…), чтение гироскопа, энкодеров, бампера |
| `lidar_walls.py` | Поток лидара и решение «есть стена или нет»: `get_walls`, `wall_present`, `wait_scan`, `measure_walls`, `measure_front_confirmed` |
| `turning.py` | `turn`, `turn_to`, `snap_target`, `angle_err`, `align_at_wall` |
| `driving.py` | `drive_cells`, `_drive_cells`, `creep_mm`, `creep_soft` |
| `bumper.py` | Всё про бампер: константы отката, `get_bumper`, `bumper_side`, реакция на удар |
| `marks.py` | Доворот на метку и перечитывание (`_turn_marks`, `_mark_stop`, `_reread_aligned`, `_front_reread`…) |
| `victims.py` | Осмотр сторон, сообщение о жертве, выдача аптечки |
| `ramps.py` | Замер и запись горок, наклон |
| `tiles.py` | Цвет плитки, синяя/чёрная, калибровка белого |
| `maze_map.py` | Карта, голосование стен, рёбра, BFS |
| `explore.py` | Обход лабиринта (`flood_fill_run`, `_DrivePlan`) и возврат на старт |
| `live.py` | Дашборд, живая карта, лифт-детектор, светодиоды — перенос как есть |

Точная раскладка каждой функции по файлам — на усмотрение исполнителя, но по смыслу таблицы.

### Как модули обращаются друг к другу

- Импорт только целым модулем: `import turning`, вызов `turning.turn_to(...)`. Так в коде видно, где лежит функция. `from x import y` между новыми модулями не использовать: это ломает общие переменные и даёт круговые импорты.
- Общие изменяемые переменные — только в `state.py`, обращение `state.maze`, `state.yaw_origin`. Никаких `global` для общих переменных в других модулях.
- Константа, нужная одному модулю, — вверху этого модуля. Нужная нескольким — в `config.py`.

### Два этапа

**Этап 1 — только перенос.** Тела функций переносятся дословно. Разрешено менять только то, что нужно для переноса: имя переменной на `state.x`, вызов на `модуль.функция(...)`. Логику, порядок, числа, тексты печати не менять. В конце этапа nav.py содержит только запуск и `main`. Этап заливается на Pi и проверяется на поле сегодня вечером.

**Этап 2 — упрощение внутри.** По одной теме, каждая — отдельный коммит и отдельная проверка на поле. Порядок по просьбе пользователя:

1. `bumper.py`: реакция на удар написана дважды (обход и возврат на старт), копии отличаются: при обходе боковой удар повторяется до `BUMPER_SIDE_RETRIES` раз, при возврате ребро сразу блокируется. Свести в одну функцию, где это отличие видно явно (параметром), поведение обеих веток сохранить.
2. `marks.py`: доворот на метку — разложить на понятные шаги.
3. `lidar_walls.py` (+ при необходимости `walls.py`): считывание стен — разложить на понятные шаги.
4. `driving.py`: `_drive_cells` (945 строк) разрезать на шаги («проверить бампер», «следить за наклоном», «проверить цвет», «доехать до центра» и т. п.). Её локальные переменные собрать в один простой объект поездки без методов-хитростей.

### Проверка (без симулятора)

- `python3 -m py_compile` всех файлов `pi/`.
- Проверка неопределённых имён (pyflakes в локальном временном venv, не на Pi) — главная ловушка переноса.
- `python3 -m unittest discover -s pi/tests`.
- Для этапа 1 — сравнение: каждое тело функции после переноса совпадает с исходным с точностью до замен `x` → `state.x` / `f()` → `модуль.f()`. Скрипт в scratchpad, не в репозитории.
- Заливка на Pi (с `.bak`), команда запуска пользователю, проверка на поле.

## Что оставлено исполнителю

- Точная раскладка функций и констант по файлам.
- Имена полей в `state.py` (по-английски, без подчёркивания в начале).
- Как модули получают `time`, `threading` и т. п. (обычный `import time` в каждом модуле).
- Нужен ли `config.py` вообще, если общих констант окажется мало.
